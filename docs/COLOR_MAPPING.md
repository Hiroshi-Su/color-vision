## 1. データの流れ全体

```
① カメラ映像 1フレーム
      ↓ ブラウザがJPEG化してPythonへ（WebSocket）
② Python (analyzer.py)
      ・ピクセルを最大10,000点サンプリング
      ・K-meansクラスタリングで「5つの代表色」に集約
      ・各色が画面に占める割合（percentage）を計算
      ・割合の多い順にソート
      ↓ hub.py が palette モードJSONに変換して ColorHub へ
③ Cloudflare ColorHub
      ↓ 接続中の全ESP32へそのままブロードキャスト
④ ESP32 (colorvision_led.ino)
      ・JSONをパース → setPaletteTarget() で144個分の目標色を計算
      ・毎フレーム現在色から目標色へブレンド → LEDへ信号送出
```

重要な設計: **色を「決める」のはPython側、ESP32は「言われた通りに描く」だけ**。
賢さをクラウド側に寄せることで、ESP32のファーム書き換えを最小限にしている。

## 2. 送られてくるデータの形（JSON仕様）

```json
{
  "mode": "palette",
  "dominant": [255, 120, 30],
  "colors": [
    { "rgb": [255, 120, 30], "percentage": 34.2 },
    { "rgb": [80,  60,  50], "percentage": 28.1 },
    { "rgb": [200, 180, 160], "percentage": 20.5 },
    { "rgb": [40,  40,  60], "percentage": 12.0 },
    { "rgb": [10,  10,  10], "percentage": 5.2 }
  ]
}
```

| フィールド | 意味 |
|---|---|
| `mode` | 描画方式の指定。現在は `palette` のみ実装（→[将来のモード拡張](#9-将来のモード拡張)） |
| `dominant` | 最頻色のRGB（現状の描画では未使用。colors[0]と同じ） |
| `colors[]` | **割合の降順でソート済み**の色リスト。各色はRGB値（0〜255×3）と画面占有率% |

- 色数は5に固定ではない。3色でも8色でも同じアルゴリズムで描画される
- 映像がほぼ単色のときはK-meansが1色しか見つけられず、1色だけのリストが届く
  （Python側の `ConvergenceWarning` はこのケースの無害な通知）

## 3. LED側の表現力

- 144個のLEDは**1個ずつ完全に独立して**制御できる
- 各LEDはR・G・B 3つの素子を持ち、それぞれ**0〜255の256段階**で発光強度を指定できる
  → 1個あたり 256³ ≒ **約1677万色**
- つまり「LEDに何色あるか」という制約はほぼなく、映像側の色をそのまま数値で渡せる

質問への直接の答え: **はい、抽出した色のRGB値（例: 茶色=120,80,60）を、
そのままLEDのR/G/Bの発光強度として渡している。** 変換テーブルやパレット制限はない。

## 4. マッピングアルゴリズム: 割合比例の帯グラフ方式

### 考え方

「5色 vs 144個」のギャップは、**多くのLEDに同じ色を持たせて『帯』を作る**ことで埋める。
LED1個1個に別の色を割り当てるのではなく、
**リング全体を「その瞬間の視界の色構成比を表す円形の帯グラフ」にする**方式。

### 具体例

解析結果が「赤34% / 茶28% / ベージュ20% / 灰12% / 黒6%」の場合:

```
LED番号   0 ............ 48 49 ......... 89 90 ....... 118 119 ..... 135 136 ... 143
         ┌────────────────┬───────────────┬──────────────┬─────────────┬──────────┐
         │   赤 (49個)    │   茶 (41個)   │ ベージュ(29) │  灰 (17個)  │ 黒 (8個) │
         └────────────────┴───────────────┴──────────────┴─────────────┴──────────┘
          ← LED 0 = テープ入力端に一番近いLED。割合の多い色から順に並ぶ
```

- **並び順**: `colors[]` の順（=割合の降順）。「左（多い）→右（少ない）」という理解で正しい。
  リングなので実際は「入力端から時計回り（配置次第）」になる
- **幅**: 34%なら 144 × 0.34 ≒ 49個分、という比例配分

### 境界の計算（丸め誤差を出さない工夫）

各色の幅を個別に四捨五入すると、合計が143個や145個になり隙間や溢れが出る。
そこで**累積割合**で境界を決める:

```cpp
// firmware/colorvision_led/colorvision_led.ino — setPaletteTarget()
int start = 0;
float cumPct = 0;
for (JsonObject c : colors) {
  cumPct += c["percentage"];                        // 累積: 34 → 62.1 → 82.6 → ...
  int end = round(cumPct / 100.0 * NUM_LEDS);       // 累積位置をLED番号に変換
  for (int i = start; i < end; i++) target[i] = 色;  // start〜end-1 を塗る
  start = end;                                       // 次の帯はここから
}
// percentageの合計が100に満たない分は最後の色で埋める
```

境界を「累積値の丸め」で決めるため、**どの帯も必ず隣と接し、合計は常にちょうど144個**になる。

### LED数に依存しない設計

計算がすべて比率ベースなので、`NUM_LEDS` を60や300に変えても**コードは一切変更不要**。
リングを買い替えても定数1つの変更で済む。

## 5. 色の遷移（フェード）

新しいパレットが届いたとき、瞬時に切り替えるとチカチカして見えるため、
**目標色（target）と現在色（leds）を分けて管理**し、毎フレーム少しずつ近づける:

```cpp
// loop() 内、20msごと（=50fps）
leds[i] = blend(leds[i], target[i], FADE_AMOUNT);   // 現在色を目標色へ40/255ずつ寄せる
```

- 受信した色は `target[]` に入るだけ。実際の見た目は数フレームかけてふわっと変わる
- `FADE_AMOUNT`（0〜255）を大きくすると機敏に、小さくするとゆったり遷移する
- カメラを動かしたときの「色が流れていく」質感はこのブレンドが作っている

## 6. 輝度の変換パイプライン

抽出したRGB値がLEDの光になるまでに、2段階のスケーリングがかかる:

```
抽出RGB (0〜255)
   ↓ × MAX_BRIGHTNESS/255      … 全体輝度制限（現在20/255 ≒ 8%）
   ↓ 電流見積り > MAX_MILLIAMPS なら全体をさらに自動減光（FastLEDの電力キャップ）
LED素子のPWM出力
```

例: 茶色 (120, 80, 60) は輝度20設定だと実際には (9, 6, 4) 相当の微弱発光になる。
**この圧縮が中間色の再現性に大きく効いてくる**（次章）。

## 7. なぜ「見た色」と違って見えるのか

RGB値をそのまま渡しているのに、原色（赤・青・緑・黄・マゼンタ・白）以外は
「それっぽく見えない」ことがある。これはLEDの性能不足というより、**原理と設定の複合要因**:

### ① LEDは「発光」なので暗い色を表現できない — 原理的限界・最大の要因

茶・灰・紺・深緑のような色は「暗さ」自体が色の一部。しかしLEDは光ることしかできない。

| 送った色 | LEDでの見え方 | 理由 |
|---|---|---|
| 茶色 (120,80,60) | 弱いオレンジ | 茶色=「暗いオレンジ」。暗さが消えてオレンジだけ残る |
| グレー (128,128,128) | 薄暗い白 | グレー=「暗い白」 |
| 紺 (20,20,80) | 暗めの青 | 同上 |

モニターが暗い色を出せるのは「黒い画面との対比」があるから。単体で光るLEDには対比がない。

### ② 輝度制限による階調つぶれ — 現在の設定での主要因

`MAX_BRIGHTNESS 20` では全値が8%に圧縮される。茶(120,80,60)→(9,6,4) のように
各チャンネルが数段階しか残らず、**色相の微妙なバランスが量子化で崩れる**。
鮮やかな原色は圧縮後も比率が保たれるため影響が小さい。→ 輝度を上げると改善する

### ③ ガンマ補正の不在 — 実装で改善可能

カメラ由来のRGBは人間の知覚に合わせた**ガンマ補正済み（sRGB）**の値。
一方LEDは値に対して**物理的に線形**に光る。この不一致で中間調が白っぽく浅く見える。

### ④ WS2812B自体の色バランス — 影響は小

青・緑の素子が相対的に強く、白がやや青白いなどのクセ。色校正もされていない。

## 8. 改善の選択肢

優先度順:

1. **輝度を上げる**: `MAX_BRIGHTNESS` 20 → 40〜60（②に効く。電力は `MAX_MILLIAMPS` が守る）
2. **ガンマ補正**: FastLEDで受信RGBに `napplyGamma_video(col, 2.2)` を適用（③に効く）
3. **色補正**: `FastLED.setCorrection(TypicalLEDStrip)` で素子バランスを補正（④に効く）
4. **彩度ブースト**: Python側でHSV変換して彩度を持ち上げてから送る
   （①への現実的な対抗策。「暗い色を無理に出す」のではなく「印象を近づける」方向）

①の原理的限界だけは設定では消えないが、作品としては
「視界の色の**印象**がLEDに流れ込む」ことが本質なので、1〜3でかなり体感が良くなる。

## 9. 将来のモード拡張

JSONの `mode` フィールドで描画方式を切り替えられる設計（ESP32側は `switch(mode)` に
描画関数を足すだけ）。LED_RD.md セクション7に設計済み:

| mode | マッピング | 見え方 |
|---|---|---|
| `palette`（実装済み） | 5色を割合比例の帯に | 色構成比の帯グラフ |
| `matrix` | 映像を低解像度化し **LED1個=映像1ピクセル** | 低解像度の動く映像（144個なら12×12） |
| `reactive` | 輝度をしきい値判定して点灯/消灯 | 明るい部分だけ浮かぶ影絵・シルエット |

paletteが「色数を圧縮する」方式なのに対し、matrixは「解像度を空間的に圧縮する」方式で、
同じ144個のLEDでもマッピングの思想が根本的に異なる。両方をモード切り替えで共存できる。

## 1. 全体構成

```
カメラ → Python解析 (analyzer/main.py, K-meansで5色抽出)
              │ 環境変数 COLORHUB_WS_URL を設定すると自動転送
              ▼
Cloudflare ColorHub（Durable Object・世界に1つの色の集会所）
   wss://color-vision-worker.color-vision.workers.dev/ws
              │ 接続中の全クライアントにブロードキャスト
              ▼
ESP32 DevKitC V4（WiFiでColorHubに直接接続・PC不要）
              │ GPIO13 から1本のデータ線
              ▼
WS2812B LEDリング 144個
```

ポイント:

- ESP32は**それ自体が完結したコンピュータ**（OSなし・書き込んだプログラム1つだけを実行）。
  一度書き込めば、以降は電源を挿すだけで WiFi接続→ColorHub接続→LED制御 まで全自動
- 同じファームを書き込んだESP32を増やせば、**電源とWiFiがある場所ならどこでも同期点灯**する
- D1/KVへの保存は `PERSIST_ENABLED=false` でオフ中。リアルタイム配信はこの設定と無関係に動く

## 2. 使用機材と仕様

### ESP32 DevKitC V4

| 項目 | 内容 |
|---|---|
| モジュール | ESP32-WROOM-32E（デュアルコア 240MHz、WiFi + Bluetooth内蔵） |
| WiFi | **2.4GHz帯のみ**。5GHz帯のSSIDには接続できない |
| USB-シリアル変換 | CP2102N（macOSは標準ドライバで認識。`/dev/cu.usbserial-XXX` として見える） |
| USB端子 | Micro-USB（miniHDMIと見間違えやすいので注意） |
| ロジック電圧 | 3.3V（GPIOの出力は3.3V） |
| ボタン | EN = リセット / Boot = 書き込みモード（通常は触らなくてよい） |

**知っておくと迷わない仕様:**

- OSがないので「シャットダウン」不要。**USBを抜く=停止、挿す=起動**
- ポート名 `/dev/cu.usbserial-130` の番号部分は**Macのどの物理USBポートに挿すかで変わる**
  （130→310など）。「ポートがない」エラーが出たらツール→ポートで選び直す
- 幅が広く、標準ブレッドボードに挿すと**片側の穴列しか空かない**（→配線章で対処）

### WS2812B LEDリング（144個）

| 項目 | 内容 |
|---|---|
| 方式 | アドレッサブルLED。**1本のデータ線**で全LEDを個別制御 |
| 配線 | 3線式: 5V（赤）/ Data（緑）/ GND（黒） |
| 消費電力 | 1個あたり最大約60mA（RGB全点灯=白のとき）。144個で理論最大8.6A |
| データの流れ | **一方通行のバケツリレー**。各LEDが自分の分を取り、残りを次へ流す |

**入力端と出力端:**

- テープには**入力（DI）側**と**出力（DO）側**がある。データは入力側からしか入らない
- 見分け方: テープ表面のLED脇に印刷された**小さな矢印**がデータの流れる向き。
  矢印が「遠ざかっていく」端が入力
- 間違って出力側に繋いでも**壊れはしない**。光らないだけなので安心して試してよい
- 両端のコネクタがオス/メスに分かれているのは**複数本を数珠つなぎ**にするため。
  1本で使うなら反対端は放置でOK

**コネクタまわり:**

- 3ピンJST-SMコネクタ（5V/Data/GND）。**メス側の穴にはオス-オスジャンパーのピンを直挿しできる**
  （はんだ付け不要。穴径がジャンパーピンとほぼ同じ）
- 4ピンコネクタ（5V/Data/Clock/GND）は**APA102など別規格用**で互換性なし
- 両端から出ている**赤黒2本の裸線は電源補助用（パワーインジェクション）**。
  USB給電の間は不使用。先端が触れないよう絶縁しておく

### ブレッドボード

- 縦の数字・横のアルファベットは**ただの座標ラベル**（電気的な意味はない）
- 電気的なルールは1つ: **中央の溝を挟んで、横並びの5穴（a〜e / f〜j）が1グループとして導通**
- ESP32は中央の溝をまたぐ向きに挿す（固いので基板の端を均等にぐっと押し込む）

## 3. 配線

### 最終形（実機確認済み）

| ESP32ピン | LEDテープ側 | ジャンパー色 | ブレッドボード上の位置 |
|---|---|---|---|
| **5V** | 赤線（5V） | 赤 | 左列の一番下（USB端子のすぐ横、CMDの隣） |
| **GND** | 黒線（GND） | 黒 | 左列、「12」と「13」の間 |
| **GPIO13** | 緑線（Data） | 緑 | 左列、GNDのすぐ隣 |

接続方法: ESP32のピンが刺さっている穴と**同じ横5穴グループの空き穴**にジャンパーを挿す。
LED側はテープ入力端のメスJSTコネクタの穴にジャンパーのピンを直挿しし、
線の色（赤/緑/黒）を辿って対応を合わせる。

### なぜGPIO5ではなくGPIO13なのか

当初の設計はGPIO5だったが、DevKitC V4をブレッドボードに挿すと**5V/GNDがある左列側しか
空き穴が残らなかった**。データ線も同じ左列にあるGPIO13に変更し、3本を片側に集約した。
ファームウェアの変更は `#define DATA_PIN 13` の1行のみ。

### ⚠️ 絶対に守ること

- **GPIO12には何も繋がない。** 起動時の内部電圧設定を決めるstrappingピンで、
  ここに配線があると起動不良を起こす（GPIO13は安全）
- **配線の抜き挿しはUSBを抜いてから**（通電中のショート防止）
- GND線は必ず接続する（電源と信号の基準。浮いていると全く光らない）

## 4. Arduino IDEのセットアップ

Arduino IDEは**Macに入れる書き込みソフト**。名前に「Arduino」とあるが、
Arduinoボードは不要で、ESP32だけで完結する（IDEが多社のマイコンに対応している）。

1. [arduino.cc/en/software](https://www.arduino.cc/en/software) からインストール
2. メニューバー「Arduino IDE」→「設定...」（⌘+,）→「追加のボードマネージャのURL」に追加:
   ```
   https://espressif.github.io/arduino-esp32/package_esp32_index.json
   ```
   ※これは「Arduino IDEにESP32の存在を教えるカタログのURL」。Espressif公式
3. ツール → ボード → ボードマネージャ → 「**esp32** by Espressif Systems」をインストール
   （数分かかる。似た名前の別パッケージに注意）
4. ツール → ライブラリを管理 → 3つインストール:

| ライブラリ | 作者 | 役割 |
|---|---|---|
| FastLED | FastLED | WS2812Bへの信号生成・電力制限・色操作 |
| ArduinoJson | Benoît Blanchon | 受信JSONのパース |
| WebSockets | Markus Sattler (Links2004) | wss://でのColorHub接続。依存関係は「Install all」 |

## 5. ファームウェアの書き込み

### ボード設定（ツールメニュー）

| 設定 | 値 | 備考 |
|---|---|---|
| ボード | ESP32 Dev Module | |
| **Partition Scheme** | **Huge APP (3MB No OTA/1MB SPIFFS)** | **必須。** TLS込みのビルドは約1.4MBあり、初期割当（1.3MB）に入らず `Sketch too big` になる |
| ポート | `/dev/cu.usbserial-XXX` | 番号はUSBポート位置で変わる |

### 手順

1. `firmware/colorvision_led/colorvision_led.ino` を開く
2. 冒頭の設定セクションで `WIFI_SSID` / `WIFI_PASS` を書き換え（2.4GHz帯のSSID）
3. ESP32をUSBでMacに接続（**データ通信対応ケーブル**。充電専用は不可）
4. **→ボタン**（左上、右向き矢印）を押す — コンパイル→書き込みまで自動
5. 「Hard resetting via RTS pin...」が出たら完了。自動で再起動して動き出す

### 書き込み後の確認（シリアルモニタ）

右上の虫眼鏡アイコン → ボーレート **115200** に設定。ENボタンで再起動すると:

```
（起動ROMの定型ログ: rst:0x1 ... entry 0x400805b4 ← 毎回出る"BIOS画面"。無視してよい）
[wifi] connecting to <SSID>....
[wifi] connected. IP: 192.168.x.x
[ws] connected: wss://color-vision-worker.color-vision.workers.dev/ws
```

`[ws] connected` が出れば、クラウドとの連携が成立している。
（FastLEDの `src/platforms/...` という内部ログが混ざることがあるが無害）

## 6. ファームウェアの動作仕様

### 起動シーケンス

1. **セルフテスト**: リング全体を 赤→緑→青（各0.4秒）に点灯
   - 配線・データ方向・COLOR_ORDERの確認用。WiFi設定前でもハード検証ができる
   - 「赤のはずが別の色」なら `COLOR_ORDER` の変更が必要（このテープはGRBで正解）
2. WiFi接続（切断時は自動再接続）
3. ColorHubへwss接続（3秒間隔で自動再接続、15秒ごとのハートビートで死活監視）
4. 色データ受信待ち。受信するとフェードしながらLEDに反映（50fps）

### 設定定数（スケッチ冒頭）

| 定数 | 現在値 | 意味 |
|---|---|---|
| `NUM_LEDS` | 144 | LED個数。**個数が変わったらここだけ変更**（描画は比率ベースでLED数非依存） |
| `DATA_PIN` | 13 | データ線のGPIO |
| `LED_TYPE` / `COLOR_ORDER` | WS2812B / GRB | LEDの型と色順 |
| `MAX_BRIGHTNESS` | 20 | 全体輝度上限 0〜255（開発中の安全値。40〜60に上げてよい） |
| `MAX_MILLIAMPS` | 400 | 電流上限。超えそうならFastLEDが自動減光 |
| `FADE_AMOUNT` | 40 | 色遷移の速さ（0〜255） |
| `FRAME_INTERVAL_MS` | 20 | 描画間隔（=50fps） |

### 受信プロトコル

ColorHubから届くJSONを `mode` フィールドでディスパッチする設計（将来のモード追加が容易）:

```json
{ "mode": "palette", "dominant": [255,120,30],
  "colors": [ {"rgb": [255,120,30], "percentage": 34.2}, ... ] }
```

現在は `palette` のみ実装。描画アルゴリズムの詳細は `doc/COLOR_MAPPING.md`。

## 7. 動作テスト

### レベル1: LED単体（WiFi不使用）

`firmware/led_test/led_test.ino` を書き込むと、赤→緑→青→白→マゼンタを1秒ずつ永久に繰り返す。
「配線の問題」と「ファーム/WiFiの問題」を切り分けられる最小テスト。

### レベル2: クラウド経由の手動送信（カメラ不要）

```bash
npm i -g wscat   # 初回のみ。以降はどのディレクトリからでも実行可
wscat -c wss://color-vision-worker.color-vision.workers.dev/ws
```

`Connected` と出たら、1行で貼り付けてEnter:

```json
{"mode":"palette","dominant":[255,0,0],"colors":[{"rgb":[255,0,0],"percentage":50},{"rgb":[0,0,255],"percentage":50}]}
```

→ リングが半分赤・半分青に変われば全線開通。

### レベル3: カメラ連動（本番構成）

```bash
cd analyzer
source venv/bin/activate
COLORHUB_WS_URL=wss://color-vision-worker.color-vision.workers.dev/ws python main.py
```

別ターミナルで `cd frontend && npm run dev` → ブラウザでカメラ開始。
視界の色がリアルタイムにLEDへ流れる。

※ `ConvergenceWarning: Number of distinct clusters (1)...` は映像がほぼ単色
（カメラが塞がっている等）のときに出る無害な警告。

## 8. 電力設計

### 基本の計算

WS2812Bは1個最大約60mA（白全点灯）。輝度にほぼ比例して減る:

| MAX_BRIGHTNESS | 144個・全白時の概算 |
|---|---|
| 20（現在） | 約0.7A |
| 60 | 約2A |
| 255（フル） | 約8.6A |

実際の消費は表示する色構成で変わる（単色RGBなら白の1/3）。

### 二重の安全装置

- `MAX_BRIGHTNESS` = 見た目の設定（全体輝度の上限）
- `MAX_MILLIAMPS` = 安全の設定（電流上限）。**超えそうな場合はFastLEDが自動で全体を
  減光して上限内に収める**ため、輝度を上げすぎても電源が落ちる前にLED側が譲る

運用ルール: **電源の能力に合わせて `MAX_MILLIAMPS` を正直に設定**し、
`MAX_BRIGHTNESS` は好みで調整する。

### 給電経路のボトルネック

USB給電時、LEDの電流は「ESP32基板のMicro-USB端子 → 保護ダイオード → 5Vピン」という
細い経路を通る。**この経路の実用上限が約1A**。Macが3A出せてもここで頭打ちになる。

| 給電方法 | 推奨設定 |
|---|---|
| Mac USB / スマホ用USB充電器（現在の構成） | `MAX_MILLIAMPS 700〜800` / `MAX_BRIGHTNESS 40` |
| フル輝度（展示など） | 5V/10A級ACアダプタを**テープの赤黒裸線に直結**し、ESP32とはGNDのみ共有（パワーインジェクション構成）。この段階でレベルシフタ（74AHCT125等）の追加も検討 |

## 9. 日常の運用

- **起動**: USB（電源）を挿すだけ。セルフテスト→WiFi→ColorHub接続まで全自動
- **停止**: USBを抜くだけ。シャットダウン操作は不要（OSがないため）
- **設定変更**: スケッチの定数を書き換え→保存（⌘+S）→→ボタンで再書き込み
- **書き込み時だけMacに接続**すればよく、普段はUSB充電器で単独動作できる
- 会場WiFiに**同意画面（キャプティブポータル）があるとESP32は突破できない**。
  その場合はテザリングやモバイルルーターを使う

## 10. トラブルシューティング実録

今回実際にハマった問題と解決策（発生順）:

| # | 症状 | 原因 | 解決 |
|---|---|---|---|
| 1 | `Sketch too big`（108%） | TLS込み1.4MB > 初期割当1.3MB | Partition Scheme → Huge APP |
| 2 | `port is busy or doesn't exist` | USBが未接続 / ポート番号変化 | 接続確認、ツール→ポートで選び直す |
| 3 | ポート一覧に何も出ない | 充電専用ケーブルの可能性 | `system_profiler SPUSBDataType` でMacが認識しているか確認。CP2102Nが見えれば配線OK |
| 4 | 4ピンJSTコネクタが3ピンテープに合わない | 4ピンはAPA102系用の別規格 | メスJSTの穴にジャンパーピンを直挿し |
| 5 | ブレッドボードで片側しか空かない | DevKitC V4の幅 | データ線をGPIO13に変更（12は禁止） |
| 6 | 黒と緑のジャンパーが逆 | 挿し間違い | GND/13に正しく挿し直し |
| 7 | **LEDが全く光らない/たまに一瞬だけ光る** | **ESP32がブレッドボードに最後まで刺さっていなかった**（ピンが穴内部の金属に未達） | **基板を奥までしっかり押し込む**。今回の最終的な根本原因 |

### 有効だった切り分けテクニック（再利用推奨）

1. **最小テストスケッチ**（`firmware/led_test/`）: WiFi要素を排除してハードだけを検証
2. **デバッグ常時点灯**: 本体ファームの `setup()` 末尾に
   `fill_solid(target, NUM_LEDS, CRGB(255,0,255));` を仮置きすると、
   経路が生きている限りマゼンタが点灯し続け、接触確認が目視でできる
   （実データ受信で上書きされるため残しても実害はないが、確認後は削除推奨）
3. **wscatによる手動送信**: カメラもPythonも起動せずにクラウド経由の疎通を確認できる
4. **「一瞬光った」は貴重な情報**: データが届いた証拠。ゼロか一瞬かで原因の候補が大きく変わる

## 1. 概要・実現可能性

Color Vision システムで抽出した色（RGB値）をJSONでLEDコントローラーに送信し、リアルタイムにLEDを光らせることは**十分に実現可能**。

Pythonがすでに色データを持っているので、そこから直接LEDに渡すのが最もシンプルで低遅延。ブラウザやCloudflareを経由させる必要はない。

### JSONフォーマット（LED側に送る想定）

```json
{
  "dominant": [255, 120, 30],
  "colors": [
    {"rgb": [255, 120, 30], "percentage": 34.2},
    {"rgb": [80,  60,  50], "percentage": 28.1},
    {"rgb": [200, 180, 160],"percentage": 20.5}
  ]
}
```

## 2. 推奨アーキテクチャ

```
Camera → Python (K-means 解析)
  ├── → ブラウザ WebSocket（既存の可視化）
  └── → LED コントローラー（新規追加）
           └── ESP32 → WS2812B LEDストリップ
```

Pythonの `main.py` に数行追加するだけで実装できる。

```python
# 既存: ブラウザに送信
await websocket.send(json.dumps(result))

# 追加: LEDコントローラーにも同じJSONを送信
await led_controller.send(json.dumps({
    "dominant": result["dominant_rgb"],
    "colors": result["colors"]
}))
```

### 通信方式の比較

| 方式 | レイテンシ | 難易度 | 向いているケース |
|---|---|---|---|
| **WebSocket（推奨）** | ~5ms | 低 | ESP32がWiFi接続できる |
| MQTT | ~10ms | 中 | 複数のLEDデバイスを制御したい |
| Serial (USB) | ~1ms | 低 | ESP32がすぐそばにある |
| HTTP polling | ~100ms+ | 低 | リアルタイム性が低くてよい |

## 3. LEDハードウェア選択肢

### 個別制御できるLEDストリップ

- **WS2812B / NeoPixel（最推奨）**: 1本のケーブルで全LEDを個別RGB制御。安価（1m数百円〜）
- **SK6812**: WS2812Bの改良版。RGBW（白チャンネル追加）でより自然な白

### コントローラー（マイコン）

| デバイス | 価格 | 特徴 |
|---|---|---|
| **ESP32（最推奨）** | ~600円 | WiFi内蔵・WebSocket対応・小型 |
| Raspberry Pi | ~5,000円〜 | Python直接実行可能だがオーバースペック |
| Arduino + WiFiシールド | ~2,000円 | 安定だが構成が少し複雑 |

### ESP32についてのよくある疑問

**Q. ESP32を使う時、ラズパイやArduinoも必要？**

→ **不要。** ESP32はそれ自体が完結した開発ボード（電源回路・USB端子・WiFi・GPIOピン込み）。ラズパイ・ArduinoはESP32の「土台」ではなく別の選択肢。

**Q. ESP32は「小さなパソコン」？Cloudflare接続の設定はどうやる？**

→ ほぼ正しいが、決定的な違いは**OSがない**こと。書き込まれた1つのプログラムだけを実行し続ける。

```
普通のPC:   OS上で複数アプリを起動・切り替えできる
ESP32:      電源を入れると書き込まれたプログラム1つが自動実行されるだけ
            （画面もキーボードもOSもない）
```

接続設定は独立した設定ファイルではなく、**プログラム自体に書き込む**：

1. PCにArduino IDE（無料の開発ツール）をインストール
2. プログラム（スケッチ）を書く。接続情報はコード内に直接記述：
   ```cpp
   const char* WIFI_SSID = "会場のWiFi名";
   const char* WIFI_PASS = "パスワード";
   const char* WS_HOST   = "color-vision-worker.color-vision.workers.dev";
   // + WebSocket接続処理 + LED描画処理
   ```
3. USBケーブルでESP32に書き込み（数十秒）
4. 以降はPC不要。**電源を入れるたびに自動でWiFi接続 → Cloudflare接続 → LED制御**

「設定する」というより「**接続処理込みのプログラムを一度焼き込む**」イメージ。
一度書き込めば、電源を挿すだけで動く「Cloudflare接続専用マシン」になる。

### 既製品スマートLED（非推奨）

Philips Hue / LIFX / Govee はAPIでRGB制御できるが、HTTP経由で100ms〜数秒のレイテンシがありリアルタイム用途には不向き。

### 必要なもの・コスト

| アイテム | 価格目安 |
|---|---|
| ESP32 DevKit | ~600〜1,000円 |
| WS2812B 1m（60LED/m） | ~500〜800円 |
| ジャンパー線 | ~200円 |
| USBケーブル | 手持ちで可 |

**合計: 1,500円前後**

## 4. 役割分担（制御の大元はPython）

**色を「決定」するのはPython。** ESP32はその指示を受けてLEDに信号を送るだけ。

```
Python（K-means解析）
  ↓ JSON送信「dominant: [255, 120, 30]」
ESP32（受信 → 信号変換）
  ↓ WS2812B用タイミング信号
LEDが光る
```

| 役割 | 担当 | やること |
|---|---|---|
| 色の決定 | **Python** | K-meansで映像から色を抽出 |
| JSON送信 | **Python** | WebSocketでESP32に送信 |
| 信号変換 | **ESP32** | JSONをLED用電気信号に変換 |
| 発光 | **WS2812B** | 信号通りに光るだけ |

ESP32はあくまで「中継役」。Pythonを止めればLEDも止まる。

## 5. 2次元LEDマトリクス対応（低解像度ライブディスプレイ）

横一列のLEDテープだけでなく、**LEDが縦横に並んだ2次元マトリクスにも対応できる**。
映像を任意の低解像度に落とし、各LEDを対応するピクセルの色で光らせる「低解像度ライブディスプレイ」方式。

### 考え方の違い

| | LEDテープ（1次元） | LEDマトリクス（2次元） |
|---|---|---|
| 処理 | K-meansで**色数を圧縮**（画面全体→5色） | 解像度を**空間的に圧縮**（画面→LED数のピクセル） |
| LEDの意味 | 色の割合を帯で表現 | 各LEDが映像の「その位置」の色を表現 |
| 結果 | 抽象的なパレット | 低解像度の動く映像そのもの |

### 実装（OpenCVなら1行）

```python
# 例: 16x16のLEDマトリクスに合わせる
led_frame = cv2.resize(img_rgb, (16, 16), interpolation=cv2.INTER_AREA)
# → 16x16x3 の配列。各要素がそのブロックの平均色
```

- `INTER_AREA` は縮小時に**ブロック内の平均色**を取る補間方式
- 「一番割合の多い色（最頻色）」にしたい場合はブロックごとに最頻値を取る。
  平均色より輪郭がくっきりした「ポスター調」になるが計算は少し重い。まず平均色で試すのが推奨

### データ量

16×16 = 256ピクセル × RGB3バイト = **768バイト/フレーム**。30fpsでもWebSocketで余裕。

### ハードウェア側のポイント：サーペンタイン配列

WS2812Bのマトリクスパネルは、電気的には**「ジグザグに折り返した1本のテープ」**。
ESP32側のコードはテープとほぼ同じで、必要なのは座標変換だけ。

```
実際の配線（サーペンタイン配列）:
→ → → → →  (0行目: 左→右)
← ← ← ← ←  (1行目: 右→左)  ← 折り返し
→ → → → →  (2行目: 左→右)

(x, y) → LEDインデックス変換:
index = y % 2 == 0 ? y * W + x : y * W + (W - 1 - x)
```

16×16パネルは市販品が1,000〜3,000円程度。

### 注意点

1. **電源**: WS2812Bは1個最大60mA。256個フル点灯で最大15A（5V）。
   USB給電では足りず**5V/10A程度のACアダプタ**が必要（輝度30%制限で大幅に削減可能）
2. **フレームレート上限**: WS2812Bの信号は1LEDあたり約30µs
   - 16×16（256個）→ 約8ms → 60fps以上可能
   - 32×32（1024個）→ 約31ms → 30fpsが上限

### K-means方式との併用

テープとマトリクスは排他ではなく、**同じPythonから「テープには5色パレット」「マトリクスには16×16映像」を並行配信**できる。

## 6. 輝度ベースのリアクティブ点灯（しきい値制御）

解析した色をそのまま光らせるのではなく、**輝度（明るさ）を算出して0〜127に変換し、しきい値（例: 64）以上なら点灯・未満なら消灯**というリアクティブな実装も可能。

### 処理の流れ

```
RGB色データ（解析済み）
  ↓ 輝度計算（1行の数式）
輝度 0〜255
  ↓ 半分にスケール
輝度 0〜127
  ↓ しきい値判定
64以上 → 点灯 / 64未満 → 消灯
```

### 輝度の算出方法

```python
# Rec.709（人間の目の感度に合わせた重み付け）
lum = 0.2126 * r + 0.7152 * g + 0.0722 * b   # 0〜255

lum7 = int(lum) >> 1        # 0〜127 に変換
is_on = lum7 >= 64          # しきい値判定
```

- 緑の重みが最大なのは人間の目が緑に一番敏感なため
- 単純平均 `(r+g+b)/3` でも動くが体感の明るさとズレる

### マトリクスへの適用（NumPyで一括処理）

```python
led_frame = cv2.resize(img_rgb, (16, 16), interpolation=cv2.INTER_AREA)
lum = led_frame @ [0.2126, 0.7152, 0.0722]   # 16x16 の輝度マップ
on_map = (lum / 2) >= 64                      # 16x16 の点灯/消灯マップ
```

映像の明るい部分だけがLEDで浮かび上がる**シルエット/影絵のような表現**になる。
データ量は 256ビット = 32バイト/フレームと極小。

### 重要: しきい値付近のチラつき対策（ヒステリシス）

輝度がしきい値（64）前後をうろうろすると、LEDが高速点滅してしまう。
対策は**点灯と消灯でしきい値をずらす**：

```python
# 点灯は70以上、消灯は58未満。間の58〜70は「現状維持」
if not is_on and lum7 >= 70: is_on = True
elif is_on and lum7 < 58:    is_on = False
```

### 発展形

| 方式 | 挙動 |
|---|---|
| 二値しきい値 | 64以上で点灯/消灯。デジタルでリズミカル |
| PWM調光 | 輝度0〜127をそのままLEDの明るさに。アナログで滑らか |
| 変化量リアクティブ | 輝度の**変化速度**で発光。動きがあった瞬間だけ光る |
| 色相×輝度ハイブリッド | 色は解析色、点灯判定は輝度。両方の情報を使う |

### MIDI連携の可能性

**0〜127はMIDIの値域と同じ。** この輝度値をMIDI CCとして出力すれば、
LEDだけでなくシンセ・照明卓（DMX機器）など音楽・舞台系の機材とも連携できる。

## 7. モード切り替え設計

パレット（5色帯）/ マトリクス（低解像度映像）/ リアクティブ（輝度しきい値）は
**モード切り替え**として1つのシステムに共存できる。

ポイントは「**JSONに `mode` フィールドを追加し、ESP32は受け取ったモードに従って描画方法を切り替えるだけ**」という構成にすること。

### JSONプロトコル（モードごとにペイロードを変える）

```json
// モード1: パレット（現在の5色帯）
{ "mode": "palette", "colors": [{"rgb": [255,120,30], "percentage": 34.2}] }

// モード2: マトリクス（低解像度映像）
{ "mode": "matrix", "pixels": [[255,120,30], [80,60,50]] }

// モード3: リアクティブ（輝度しきい値）
{ "mode": "reactive", "on_map": [1,0,1,1,0] }
```

### 役割分担

```
フロントエンド（Nuxt）
  └ モード切り替えUI（ボタン3つ）
       ↓ WebSocketでモード変更を通知
Python
  └ 現在のモードに応じた解析・変換を実行し、modeフィールド付きJSONを送信
       ↓
ESP32
  └ switch(mode) で描画関数を切り替えるだけ。状態は持たない
```

**モードの状態はPython側で一元管理**するのがポイント。
ESP32は「言われた通りに描く」だけにしておくと、モードが増えても
ファームウェアの書き換えが最小限で済む。

### ESP32側の実装イメージ

```cpp
void onMessage(JsonDocument& doc) {
  const char* mode = doc["mode"];
  if      (strcmp(mode, "palette")  == 0) drawPalette(doc["colors"]);
  else if (strcmp(mode, "matrix")   == 0) drawMatrix(doc["pixels"]);
  else if (strcmp(mode, "reactive") == 0) drawReactive(doc["on_map"]);
}
```

### 切り替えのトリガー候補

| トリガー | 用途 |
|---|---|
| フロントエンドのUIボタン | 手動切り替え（基本） |
| 時間で自動ローテーション | 展示で放置運用する場合 |
| 映像の内容で自動切り替え | 動きが激しい→リアクティブ、静か→パレット、など演出として |

## 8. 発展構想：グローバルLED同期 × 観客参加型

R&D案A（グローバルLED同期）と案E（観客参加型）の融合。「観客の視界の色が、世界中のLEDを染める」。

### パターンA：色だけ欲しい場合（推奨・シンプル）

実は**Cloudflare Realtime（SFU）すら不要**。

```
観客のスマホ（10〜100台）
  │ ブラウザ内で色抽出（Canvas API）※映像は送らない
  ↓ WebSocket（数百バイト/秒の色JSONのみ）
ColorHub（Durable Object）← 世界に1つの「色の集会所」
  │ 全員の色を集約（平均・モザイク・時間差ミックス）
  ↓ 一斉配信
  ├→ 東京の会場のLED（ESP32）
  ├→ 大阪のLED（ESP32）
  ├→ 会場の大型ディスプレイ
  └→ 海外ギャラリーのLED
```

成立する理由：
- 色抽出はスマホのブラウザ（Canvas API）で完結できる
- 送るのは小さなJSONだけ。映像ストリーミングのコストも遅延もない
- ColorHubは実装済み。ESP32もスマホも「同じWebSocketのクライアント」として対等

### パターンB：映像も見せたい場合

観客の映像そのものをスクリーンに映すなら Cloudflare Realtime（SFU）+ RealtimeKit を併用する二層構成。

```
観客のスマホ ──映像──→ Realtime SFU ──→ 会場スクリーン（映像合成）
      └──色JSON──→ ColorHub ──→ LED群（世界中）
```

### 比較

| | パターンA（色のみ） | パターンB（映像付き） |
|---|---|---|
| 使うサービス | Durable Objectsのみ | + Realtime |
| 実装難易度 | 低 | 中〜高 |
| 体験 | みんなの視界の色が空間を染める | 自分の映像も作品に映り込む |
| 推奨 | **まずこちらでプロトタイプ** | 展示機会が決まったら拡張 |

### 各LED拠点にローカルPCは不要

ESP32はWiFi内蔵なので、**ESP32自身がWebSocketクライアントとしてCloudflareに直接接続する**。PCの仲介はいらない。

```
【送信側】東京（ここだけPCが必要）
  カメラ + PC（Python解析）
        ↓
  Cloudflare ColorHub（Durable Object）
        ↓ インターネット経由のWebSocket
【受信側】各会場（PC不要）
  大阪:  ESP32 + LED + USB電源 + 会場のWiFi  ← これだけ
  海外:  ESP32 + LED + USB電源 + 会場のWiFi  ← これだけ
```

各拠点に必要なのは：

| 必要なもの | 備考 |
|---|---|
| ESP32 + LED | 本体 |
| USB電源 | スマホ充電器でOK |
| WiFi | 会場のWiFiに接続 |

「電源とWiFiさえある場所なら、手のひらサイズのデバイスを置くだけ」で世界中どこでも同期先にできる。

### 実運用での注意点

1. **wss://（TLS）対応**: Cloudflareへの接続は暗号化必須。ESP32のWebSocketライブラリ（`WebSocketsClient`など）はSSL対応済みなので問題なし
2. **WiFi設定**: 会場ごとにSSID/パスワードが違うため、ファームウェアに埋め込むか、`WiFiManager`（初回起動時にスマホから設定できる仕組み）を入れておくと現場で楽
3. **会場WiFiの罠**: ホテル・商業施設のWiFiは「ブラウザでの同意画面（キャプティブポータル）」があるとESP32が突破できない。その場合はモバイルルーターかスマホのテザリングを持ち込むのが確実

## 9. ロードマップ

     （144LED、`NUM_LEDS` 定数1つで個数変更可、percentage比率描画でLED数非依存、

   - ✅ **実機開通（2026-07-15）**: wscat→ColorHub→ESP32→LED、および

     セットアップ手順・仕様は `doc/LED_ESP32_SETUP.md`、

   - 複数クライアントの色の混ぜ方（平均 / 人数割合で帯分け / 時間差リレー）が作品のコア
